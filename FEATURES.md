**2026-08-21 (v2.38.1): the quote status push stops wiping the quote's Reference.** Reported from the app: every quote in Xero had a blank Reference, despite one being typed on Summary every time. The create call was never at fault — it sent `Reference` correctly and Xero stored it. A **second** write erased it. Marking a job Accepted/Declined calls `/update-quote-status`, which POSTs the quote back to flip its status, and because this app creates every quote as DRAFT that write happens twice (the `DRAFT -> SENT` hop, then the answer). Its payload was `{QuoteID, Contact, Date, Status}` and nothing else, on the stated assumption that "everything else (line items, terms) is left off and survives untouched". Half true, and the true half is exactly what hid it: an **omitted `LineItems` array** IS special-cased by Xero and left alone, so the quote always still had its lines and nothing looked broken. Scalars are not. Per Xero's own Quotes documentation you are always updating the *entire* quote, so `Reference`, `Terms`, `Summary`, `Title` and the expiry date were being blanked on every status change — the payment-terms text on accepted quotes went the same way. Both writes now echo those five fields back from the GET the route already makes (i.e. whatever is in Xero right now, so an edit made inside Xero isn't stomped either) and change only the status; empty ones stay `undefined`, which is the same nothing they already were. The in-place amend path in `/create-quote` had the same class of bug one step milder — it passed `Reference` but cleared `Title`/`ExpiryDate`, and would clear `Terms`/`Summary` on any send that didn't rebuild them — so it carries those over from `existing` now too. Verified by a stubbed harness (axios + db mocked, the real router driven): the old payload sends `Reference: undefined` on both writes, the new one carries the reference through both with `LineItems` still omitted. **Quotes already wiped don't self-heal** — re-sending an amendable quote restores the reference from the Summary box; ones already accepted or invoiced need it re-typed in Xero. Server-side only, no client or DB changes.

**2026-08-20 (v2.38.0): accepted quotes stop moving.** `ACCEPTED_SNAPSHOT_SPEC.md`. Every figure in this app is DERIVED — rooms store dimensions not prices, the materials snapshot stores quantities not coverage rates, labour lives on the Rates page as minutes-per-m² — so opening a quote re-runs `calcRoom()`/`computeMaterials()`/`computeDepositPlan()` over whatever those constants say *right now*. Right for a draft; silently destructive the moment a client says yes. Nudge a coverage rate or recalibrate the day rate and **every accepted quote in the app re-priced itself**, with no edit, no audit trail and nothing on screen to say the number had moved — invoiced jobs included, since the final invoice billed "labour as quoted" by re-running the quote's own maths. Now: at acceptance the pipeline runs **once** and its whole output is serialised into a new **`quote_snapshots`** table — **run `db/setup.sql` on deploy** (also created lazily on first use, so a missed deploy step doesn't 500). The table is **append-only by construction**: `routes/api.js` exposes GET and POST and nothing else, the POST is a bare INSERT with `version` derived as `COALESCE(MAX(version),0)+1` *inside* the statement (so two devices accepting at once collide on `quote_snapshots_job_version` and the loser 409s and retries rather than overwriting — verified, 8 concurrent POSTs → 7 rows at 7 distinct versions), and rows leave only via `DELETE /jobs/:id`. A table rather than another key on `jobs.data` precisely because that blob is PUT-merged whole on every status change and note edit. Each snapshot carries the client-facing quote model (so a frozen quote reopens as the exact page the client was shown), flat line items, the materials breakdown **including the calc's own working** — litres per role, product/band, tin combination — the labour breakdown with all three pricing modes recorded (calculated-days / standalone diary-days / honoured, not just the winner), markup + commercial + standalone flags, ex-VAT/VAT/inc-VAT (`vatRegistered:false`, `vatRate:0` — not registered, every Xero document goes out `NoTax`; recorded anyway so a pre-registration snapshot stays unambiguous), and **the whole Rates page verbatim**, which is what makes a drift question answerable instead of arguable. Lines are rounded ONCE and every total is the sum of the rounded lines, so the document, Summary and the invoice tie out to the penny forever. `jobQuoteIsFrozen()` — accepted/completed/invoiced AND a snapshot exists — is the single predicate every path branches on: the client quote preview and PDF return from the snapshot **before a single calc call** (PDF named `…-accepted-revN.pdf`, footer rewritten so it can't say "figures are live"), Summary's hero shows the agreed total with the live recalculation demoted to a labelled aside ("Same job at today's rates: £X — not what was agreed"), the Room Breakdown stays live but relabelled as working, the final invoice's quoted-labour lines are replaced wholesale by the frozen rows (still droppable — what's fixed is the price, not whether it's billed), and profitability's quoted side reads the snapshot so margin on finished work stops drifting. Deliberately still live: drafts, actuals, the labour log, variations (priced at today's rates *because that's when they were agreed*) and scheduling. **Amend is never an edit** — it appends `version+1`, shows the before/after delta, asks what changed, and leaves every earlier revision exactly as written and viewable; un-accepting resumes live pricing but does NOT destroy the record. Three guardrails: structural (no write endpoint exists), runtime (`deepFreezeSnapshot()` — a render path that mutates a snapshot throws instead of quietly rewriting agreed figures), and static (`npm run check:snapshots`, which catches the failure the other two can't — an accepted-render path going *back* to the live calc — by asserting the server surface, that the frozen renderers touch none of the twelve calc functions, that `openClientQuote()` branches before any calc runs, and that snapshots are written from one function only; comments and string literals are blanked before scanning so the check can document itself without tripping over its own prose). Captures survive no signal: acceptance happens on site, so they queue in localStorage, render immediately, and flush on reconnect — the generic offline queue can't carry them since it dedupes by path and every capture posts to the same one. A job accepted **from Xero** while another job is open records the debt and captures on first open, flagged "captured late"; jobs accepted before this shipped are deliberately NOT self-healed (months old, today's rates say nothing about what was agreed) and instead get a red banner saying in as many words that their figures are live, not frozen — a state that was previously invisible. Verified by `npm run test:snapshots`: 38 checks driving the real app in Chromium against a real database, centred on doubling the day rate, halving wall coverage and adding 25 markup points, then proving the LIVE figure moves (£1,367.51 → £2,823.87) while every AGREED figure stays at £1,367.51 across Summary, the client quote, the PDF and the invoice.

**One-off migration for the damage already done: `npm run migrate:accepted-snapshots`** (`scripts/migrate-accepted-snapshots.js`, dry-run by default, `--apply` to write, safe to re-run). Historical accepted quotes have no snapshot and have been silently re-priced for however long. The script does **not** recompute anything — recomputing is the bug — it rebuilds from Xero, where the documents the client actually received have been sitting unchanged: linked `xeroQuoteId`/quote number first (itemised → `xero_lines`), then the linked invoice (real money, but it's the *bill*, so the snapshot carries an explicit caveat that variations and materials-as-used are inside it), then contact+reference+date proximity, which is **listed for review and never applied without `--allow-fuzzy`**. A document with no priced lines becomes `totals_only` — one honest lump, `rates` and the labour fields left null, because inventing a plausible split would be worse than saying so: a plausible split gets believed. Jobs with no Xero record are left alone and listed alongside whatever figure the app is currently showing. The "lock" is simply the snapshot's existence (with a row present, no future rate change can reach the job); job status is deliberately NOT rewritten, since these jobs are already accepted/completed/invoiced and touching a lifecycle field to lock something already locked would only risk moving a job backwards in the pipeline. `--file <export.json>` runs it against a Xero export with no live connection. The report names the drift it found per job ("app was showing £4,100.00 — out by £280.00").

**2026-08-20 (v2.37.0): paint quantities on the room form.** The litres a room needs have always existed — `calcRoom()` returns `wallL`/`ceilL`/`glossL`/`primerL`/`mistL`/`panelL`/`featureWallL`, and `computeMaterials()` pools them across the job into Summary's materials list — but on Measure they were invisible: the room form's Preview card stopped at wall area, ceiling area, cost and time, so the only way to see what a room actually buys was to leave the form and read a job-wide figure with every other room already folded into it. A miscounted coat or a spray toggle left the wrong way was therefore only ever visible *after* it had been averaged in with everything else. New **Paint Needed** card under Preview, one row per surface — Walls, Feature wall, Ceiling, Woodwork topcoat, Woodwork primer, Mist coat, Panelling — live as you type, from `renderRoomPaintLitres()`, which **reads the calc rather than repeating it**: no litre is worked out twice anywhere in this change. Surfaces needing nothing keep their row hidden and a line buying no paint at all (wallpaper-only, or a door count before any coats are set) hides the whole card rather than showing a column of dashes. Two details worth naming. **A same-paint feature wall shows as ONE Walls figure**, not two rows: `featureWallSharesWallPaint()` — the same rule `computeMaterials()` pools by — decides, and the card then shows `wallLCombined`, rounded up once over the combined area, under a row that relabels itself "Walls (incl. feature wall)" so the fold is visible rather than silent; two rows each rounded to their own half litre would add up to more than the job buys (5.0L reads as 4.0 + 1.5 apart). For that check to answer the same way the saved room will, the preview's throwaway room object now carries `colourNumber`/`featureWallColourNumber` and the wall/feature-wall **band** overrides — nothing in `calcRoom()` prices off any of them, they exist purely so "same colour and same product" resolves identically before and after Save. **Staircase rooms get the card too**, which the Preview card itself never managed: their litres need the geometry-derived overrides (`wallAreaOverride`/`ceilAreaOverride`/`woodAreaOverride`) that only `computeHSLOverrides()` produces, since an HSL room's own l/w/h are the dummy 1×1×1 placeholders. Rather than re-derive skirting area, self-priming coat swaps and panel primer a second time inside `calcHSLNow()`, it runs the real `calcRoom()` over `buildRoomFromForm()` — byte-for-byte the room the form is about to save — so the figures shown are the ones Summary will buy the moment it is saved. Figures are estimates in the usual sense: your coverage rates (per-product where one is on record, the flat rate otherwise), spray uplift included per surface toggle, rounded up to the half litre — the card's header says so. Verified by a 35-check fake-DOM harness over both room types (hand-checked walls/ceiling arithmetic, every row against the calc field it claims to show, the combined-feature-wall fold, zero-coat and empty-form hiding, and a staircase's litres landing on the wall area its own results card reports) plus a 5-check cross-test proving a one-room job's card matches `computeMaterials()` role for role. Display only — no pricing, calc or DB changes.

**2026-08-19 (v2.36.1): a copied ROOM no longer inherits the client's signature.** Spotted while giving fitted units the same ⧉ (v2.36.0 above, which got this right from the start): `duplicateRoom()` deep-cloned the room wholesale, `variationStatus`/`variationApprovedAt`/`variationApprovalNote` included — so duplicating an **approved** variation room produced a second room the client had never been shown, already carrying their ✓ and the original's approval note ("agreed via text 14 Aug"). Money-wise a pending copy would have billed the same — approved and pending variations both count, only declined ones drop out — so the damage is the RECORD: the Variations card shows work as agreed that nobody agreed to, it never appears in the pending count that prompts a sign-off, and `computeVariationsView()` folds the inherited `approved` into the approved-only `appLabour`/`appSpray` aggregates behind the profitability view. The same clone was wrong in the other direction on an accepted job: copying an **original-scope** room left the copy un-flagged, silently joining the quoted scope — exactly the billing bug v2.34.1 closed for newly-added fitted units. `duplicateRoom()` now does what `duplicateFittedUnit()` does: the three sign-off fields are deleted (so the copy reads Pending through `variationStatusOf()`'s default, and appears in the Variations card awaiting a real answer) and `copy.isVariation = src.isVariation || variationDefaultsOn()`. The original is untouched — it keeps its ✓ — and the existing panelling/excluded-wall id refresh still runs, so copies never share row ids. On a draft job nothing changes at all: `variationDefaultsOn()` is false, so a copy of ordinary work stays ordinary work. Verified in a browser across both job states. No DB changes.

**2026-08-19 (v2.36.0): fitted units can be duplicated.** Rooms have had the ⧉ copy button since the Measure list was built (`duplicateRoom()` — "bedrooms 2/3/4 are usually the same room with different dimensions"), and fitted units are the same story with more fields to retype: two alcove units either side of a chimney breast differ by a bay width or two, and since v2.21.0/v2.25.0 a unit carries per-bay widths, a height, a depth, a door size band, a both-sides flag, prep level, complexity, colour and product. `duplicateFittedUnit(id)` mirrors `duplicateRoom()` exactly — JSON deep clone (the `bayWidthsM` array included), fresh `uid()`, "(copy)" suffix on the name, spliced in at `idx + 1` so related units stay together, persisted through the same `saveFittedUnitJob()` wholesale job-data PUT as every other unit change (so it syncs and queues offline identically) — with the ⧉ button on the unit's Measure card, inside the existing `swipeDeleteWrap()` and `event.stopPropagation()`'d off the tap-to-edit, byte-for-byte the rooms markup. **Two things the copy deliberately does not inherit**, both places where cloning wholesale would be wrong rather than merely different: the **client's sign-off** (`variationStatus`/`variationApprovedAt`/`variationApprovalNote` are deleted — an approval belongs to the unit the client actually agreed to, and a copy is unagreed work that starts Pending), and an **un-flagged variation state on an accepted job** (`copy.isVariation = src.isVariation || variationDefaultsOn()`, the v2.34.1 default for any new unit — a unit added after acceptance that silently joins the original scope is the billing bug that fix closed; a copy of a variation is always one too). Rooms' own `duplicateRoom()` still clones both of those wholesale — flagged, not changed here, since it is long-standing behaviour outside this ask. No DB changes.

**2026-08-19 (v2.35.0): door faces — both sides on fitted units, outside-only on kitchens.** The interior door rate is a **per-face** rate (`doorFaceAreaM2` = 1.75m², half a ~3.5m² leaf; `doorMins()` per face), and the two cabinet modules each hard-coded the usual case in opposite directions. **Fitted units** priced every cabinet door at one face — correct for a built-in painted from the front, wrong the moment the backs are sprayed, with no way to say so (doubling the door count would also have doubled the size band's effect on litres, and there was no per-door dimension to reach for). New per-unit **`doorBothSides`** toggle under Door size on the Fitted Unit form: `calcFittedUnit()` gains a `doorFaces` multiplier applied to BOTH the door minutes and the door face area, so labour and litres move together exactly as the v2.21.0 size band does — shelf and bay figures untouched. **Kitchens** are the mirror image: the flat per-piece prices in Kitchen Rates are whole-piece, both-faces figures, so a kitchen where only the outsides are sprayed had no expression at all. New per-job **`singleSide`** toggle in a new **Faces** card at the top of the Kitchen form: `calcKitchen()` applies `sideMult` = 0.5 to the four per-piece totals (doors, drawer fronts, end panels, fillers) **after** `typeTotal()`, so the glazed/curved premium halves with the piece it belongs to instead of surviving at full price. Deliberately narrow — three things do NOT halve: the **carcass %**, whose base stays the FULL piece totals (the carcasses behind the doors are the same surface however much of the door is painted, so halving the base would quietly halve a charge for unchanged work); **cornices/plinths**, linear trim with one face to begin with; and **stripping**, whose per-tier minutes are a whole-piece figure calibrated against real doors (flagged, not fixed — say if it should follow the toggle). Both flags are **off by default and absent reads as off**, so no existing quote or fitted unit moves — verified against a 27-check harness over both calcs (absent === explicit-off on totals and litres; small+both-sides === standard one-face; complexity uplift still stacking on the doubled door minutes; a kitchen's total dropping by exactly half its piece work and by nothing else). Visible where it's priced: the Fitted Unit and Summary breakdowns label the door line "— both sides", the Kitchen and Summary breakdowns label the four halved lines "(outside only — ×½)", and outside-only rides the CLIENT-facing scope too — the in-app quote's kitchen line reads "outside faces only" and the Xero line description carries the same suffix (sent explicitly even with no quote-text block, so the server's plain-'Kitchen Cabinet Spraying' fallback can't lose it). Job duplication carries both flags for free (both routes spread the object wholesale). No DB changes.

**2026-08-19 (v2.32.0): Deposits go into Xero as real prepayments** (`DEPOSITS_SPEC.md`). Until now the app never *recorded* a deposit at all — `computeDepositPlan()` forecasts one (25% of quote, or materials+sundries, whichever is greater) and the final-invoice screen takes a **reference-only** figure that changes nothing, per the 2026-07-22 decision that payments get applied in Xero. The real deposit was being typed into Xero by hand as Receive Money → "Received as Prepayment". Two halves ship here. **(1) `job.deposit` — the first record of money actually received** (amount, date received, note), on the Summary status card from `accepted` onward, prefilled from the plan figure but freely editable because it records what was *actually paid*, not what should have been. **(2) The Xero push:** a prepayment cannot be POSTed — `/Prepayments` is read-only — so it's created as a **BankTransaction of `Type: RECEIVE-PREPAYMENT`**, which hands back its `PrepaymentID` on the same response (no matching step, no drift). `POST /auth/create-prepayment` reads the bank account and posting code (**620 Prepayments**) from the SERVER's settings row, never the request body — the browser doesn't get to name where real money posts — pre-flights the account code (only a positive "missing or archived" blocks the write; a failed lookup lets the real call judge), and sends an **`Idempotency-Key` stored on the deposit and reused on every retry**, so "Try again" can never create a second prepayment. ## Architecture reminder

- **Frontend:** `public/index.html` — single-file vanilla JS app
- **Backend:** `routes/xero.js` (OAuth + quote/contact/item endpoints), `routes/api.js` (rooms, exterior items, settings, HSL)
- **Database:** PostgreSQL on Render (rooms, exterior_items, settings, hsl_state tables)
- **Deploy:** push to GitHub `main` → Render auto-deploys
- **Xero:** connects with `accounting.contacts`, `accounting.settings.read`, `accounting.invoices`, `accounting.banktransactions` and `accounting.payments` scopes (the last two added 2026-08-19 for deposits, `DEPOSITS_SPEC.md` — proved permitted first via `GET /auth/scope-check`). **This app uses GRANULAR scopes** (see its developer-portal Authorisation list): `accounting.invoices` is the valid quotes+invoices scope here, and the coarse `accounting.transactions` is NOT permitted — requesting it fails the whole auth with `invalid_scope` (the 2026-07-22/23 reconnect saga, resolved v1.10.6). Old doubts about `accounting.invoices` being "not a documented scope" were wrong for this app type.

## Key gotchas learned during the build

- **Duplicate functions:** the app has had repeated bugs where an old version of a function survived alongside a new one, with the later definition silently overriding the earlier. When something doesn't behave as expected, grep for duplicate `function X` definitions first.
- **extItems vs old extCost:** exterior items use the `extItems` array + `calcExtItem()`, loaded from `/api/extitems`. Old code used `extCost`/`extTime` globals — make sure any new code (Xero quote, CSV) reads from `extItems`, not the old globals.
- **Data sync:** rooms and exterior items load from the server into memory on init. Render functions should read from the in-memory arrays. Avoid reintroducing localStorage as a competing source of truth.
- **Whole-tin rounding must happen at job level**, not per room, or multi-room jobs over-count tins.

- **Working time** — e.g. 2.85 days (drives labour/cost, unchanged)
- **Estimated on site** — e.g. ~4 days (what to block out in the diary)

### Approach — per-day overhead + optional buffer
- **Per-day overhead** (Settings, editable) — a fixed non-productive allowance per day on site (setup, protection, masking, cleanup — say 45–60 mins). Reduces effective productive hours/day, which stretches calendar days. Scales correctly: more days = more accumulated setup/cleanup.
- **Optional buffer multiplier** (Settings) — a modest × for drying/slippage on top, if wanted.
- Keep it to "realistic days on site" — don't try to model drying times precisely or manage the diary; that's calendar territory.

### Why it must come before the deposit feature (KEY LINK)
The staged-payment logic keys off job length — and it must use REALISTIC time, not working time. Example: 6.85 working days looks like just over one week, but realistically spans **two working weeks**, which is exactly when weekly staged payments apply. If the payment logic used raw working days it could treat a two-week job as single-week and miss the staging.

Chain for staged payments: working time → realistic time (× overhead/buffer) → working weeks (realistic days ÷ 5, or however weeks fall) → number of weekly payments.

### Client-facing (optional)
Having the realistic duration to hand is also better for telling the client "about a week" — the raw working time would sound too short and set wrong expectations.

## FEATURE: Spray walls toggle ✅ SHIPPED (2026-07-21)

Per-room "Spray walls" toggle (its own collapsible card on the room form, after Mist Coat). **Materials-only** — labour deliberately stays on `wallMins()`, on the working assumption that spray application speed vs masking time is a wash on the rooms you'd actually choose to spray.

- **Only the wall rate forks.** Ceiling, woodwork and mist coverage rates were already calibrated assuming spraying, so they're untouched. A second coverage setting, **Wall Emulsion — Sprayed** (`cwSpray`, default 9 m²/L vs rolled 13), sits next to the rolled rate in Coverage Rates; `calcRoom()` picks one per room for `wallL` and `featureWallL`. Calibrate it against real sprayed jobs like the other rates — the default is a guess.
- **Spray sundries bump** (`sundriesSprayPct`, default 3%): sprayed rooms use extra masking film/tape/paper, so their labour carries an extra sundries % on top of the job-wide rate — sprayed rooms' labour only, not the whole job's. `calcRoom()` exposes `sprayLabour` per room and `computeDepositPlan()` takes the summed figure, so Summary and the Xero quote share one number (the usual drift-bug guard). This default is also a guess — calibrate.
- Room flag `sprayWalls` rides the standard lifecycle (temp var, `buildRoomFromForm()`, `editRoom()` restore, draft capture) and defaults off, so old rooms and quick-added rooms stay rolled. HSL rooms get it generically like mist.
- Litres flow into the existing tin optimiser/Xero pipeline unchanged — the toggle just changes the input litres.
- **Exterior render (added 2026-07-22):** same pattern on exterior items — per-item "Spray render" and "Textured render" toggles in the Masonry/Render card, forked inside `extMasonryLitres()` across a **2×2 of coverage settings** (smooth/textured × rolled/sprayed: `extMasonryCov` 6 · `extMasonryCovSpray` 4 · `extMasonryCovTex` 4 · `extMasonryCovTexSpray` 3 m²/L) — texture gets its own rolled/sprayed pair rather than a multiplier on the smooth rates, since it soaks up more paint however it's applied. The spray sundries bump extends to exteriors on the same `computeDepositPlan()` contract, with one deliberate difference: the basis is the **masonry labour share only** (incl. its prep), not the whole item — an exterior item can be dominated by window restoration that has nothing to do with spraying render, so whole-item labour would be the wrong masking proxy. `calcExtItem()` exposes `sprayLabour` on the same contract as `calcRoom()`. **Texture, unlike spray, DOES fork labour** — working paint into textured render is genuinely slower, so `extMasonryMins()` picks a textured mins/m² rate (`rExtMasonryTex`, default 7 vs smooth 5). One textured rate covers rolled and sprayed alike: spray never changes labour, texture always does. Texture never touches the sundries bump directly (masking doesn't care about texture), though a textured item's higher masonry labour does raise the bump's basis when it's also sprayed — intended, bigger labour = same % of more.

## FEATURE: Material tracking (actuals vs estimate — job management) ⬜ NOT STARTED, SCOPED

DIFFERENT from everything else so far — everything to date is ESTIMATING (what a job should cost). This is ACTUALS: track what was really used/purchased against a job so nothing's missed at invoicing (forgotten materials = lost money). Turns the app from a quoting tool into a light job-management tool.

> **NOTE: now specced in `MATERIAL_TRACKING_SPEC.md`, which SUPERSEDES the "scope carefully when reached" note that used to live here.** That doc is authoritative: the quantities-only/derived-money decision, the `material_actuals` data model, the three-phase build order, and the open question of where it lives.

Headlines from the spec:
- **Materials are quoted as an ESTIMATE and invoiced as USED.** This is the billing model, and it makes tracking load-bearing rather than a safety net: actuals ARE the invoice's materials list, not just a note of what got forgotten. Labour is quoted and billed as quoted; only materials float.
- **Quantities only in, money derived out — all of it.** Account codes confirmed: **202** sales, **311** paint cost, **314** specific-sundry-item cost. All ride on the `/Items` payload the app already fetches, so billable value AND margin come from a typed quantity. No manual pricing anywhere.
- **314 is NOT the cost side of the sundries %.** The % (labour × %) covers stock consumables used across jobs — caulk, tape, filler, floor protection — at normal usage, and stays a percentage; the % itself is never itemised, never tracked. 314 is for job-specific consumables the % won't cover (wallpaper paste, lining paper), which are real Xero items tracked like paint. Itemising something the % already covers **as routine** charges the client twice — but **floor protection is a deliberate exception**: the % pays for the normal amount and an itemised line pays for the unusual extra a job needed, which is additive rather than a double charge. See the Gotchas in `MATERIAL_TRACKING_SPEC.md`.
- **A prerequisite surfaced (Phase 0):** `groupMaterialItems()` drops any item whose name has no parseable size, so paste/lining paper are probably absent from the picker today — the exact items the specific-sundries flow needs. Small fix, needs verifying against the live payload.
- **Actuals must NOT live on materials-snapshot lines.** `recalculateMaterialsSnapshot()` is a full overwrite that regenerates every line id, so actuals stored there would be silently destroyed by a normal mid-job Recalculate — destroying the invoice, under this billing model. They get their own `material_actuals` table, joined by `itemCode` (stable) rather than line id (not stable).
- **The app has no invoice path** — it only creates Quotes. Billing actuals means either outputting a list to enter in Xero (recommended start) or building `POST /Invoices`.
- **Xero can't supply purchases.** No `accounting.transactions` scope, so logging stays manual — fine, since only quantities are typed.
- Depends on Multiple saved jobs (tracking is per-job) — now shipped, so this is unblocked.

## Xero quote PDF templates (custom DOCX)

The Xero quote branding uses **custom DOCX templates** (downloaded from Xero → Settings → branding themes). These are editable via Claude Code (docx skill), unlike Xero's built-in theme editor. Use this to make the growing quote — materials line items, sundries line, deposit/payment terms — display cleanly, especially a long itemised materials list that looks cramped in the default layout.

**How they work:** Word documents with Xero **merge fields** (e.g. `«LineDescription»`, `«LineAmount»`, `«Total»`) that Xero swaps for real data at generation time. Claude Code can restyle/rearrange layout, spacing, columns, fonts and the arrangement of merge fields.

**Constraints / cautions:**
- Can only use merge fields Xero actually supports, named EXACTLY — can't invent new ones. If you want data shown (e.g. deposit amount), there must be a Xero merge field for it, or it comes through as a line item / terms text.
- A branding theme can have separate templates (quote, invoice, etc.) — be explicit which one is being edited. The quote has multiple pages (cover letter, itemised quote, terms, cancellation) — specify which.
- **BACK UP the working template before editing.** A renamed field or broken structure can make quotes generate wrong or fail to populate. Edit a copy, keep the original safe.
- **Test on a real draft quote in Xero before going live** — merge-field templates can look right in Word but only prove out when Xero renders them with real data. Check branding, materials flow, totals and terms all populate.

**Process:** download current template from Xero → give the DOCX to Claude Code → tell it what's being added and how it should look → it edits keeping branding + merge fields intact → re-upload to Xero → test on a draft.
