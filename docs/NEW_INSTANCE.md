# New Customer Instance — Runbook

How to stand up (and later retire) one customer's instance of NH
Estimator. Isolation model per `MULTI_INSTANCE_PILOT_SPEC.md`: every
customer gets their **own web service + own Postgres database**, their own
Xero connection, and their own `APP_PASSWORD`. Nothing is shared between
instances. Budget ~30 minutes, most of it waiting for the first deploy.

## 1. Create the services on Render

Use the repo's `render.yaml` blueprint — it is the canonical definition of
an instance (web service + database + env vars + the provision step).

- **Separate workspace per customer** (recommended: cleanest billing and
  no name collisions): New → Blueprint → pick this repo → apply.
- **Shared workspace:** rename both `name:` fields first (e.g.
  `nh-estimator-smith` / `nh-estimator-smith-db`) so they don't collide
  with existing services, then apply.

The blueprint prompts for the `sync: false` values:

| Env var | Value |
|---|---|
| `APP_PASSWORD` | The password this customer will sign in with. Generate a decent one; they can't change it themselves — you set it here. |
| `APP_URL` | `https://<service-name>.onrender.com` |
| `XERO_CLIENT_ID` / `XERO_CLIENT_SECRET` | From the Xero developer app (developer.xero.com) |
| `XERO_REDIRECT_URI` | `https://<service-name>.onrender.com/auth/xero/callback` |

`SESSION_SECRET` is auto-generated by Render; `DATABASE_URL` is wired to
the new database automatically. **Do not set `DEBT_APP_ENABLED`** — that
flag is for the owner's personal instance only.

The first deploy runs `npm run provision` automatically (schema + colour
library, idempotent), so the database is ready with no manual `psql`.

## 2. Xero developer app

On the Xero app's configuration page (developer.xero.com → the app), add
this instance's callback URL to the **redirect URIs** list:
`https://<service-name>.onrender.com/auth/xero/callback`.

Mind the limit: an uncertified Xero app can be connected to **25
organisations** total across all instances. Fine for the pilot; Xero App
Store certification lifts it if this ever scales.

## 3. Hosting hygiene

- Turn on **daily Postgres backups** for the new database (Render
  dashboard). The in-app JSON export is a user-level backup, not disaster
  recovery for someone else's business.
- Once WS5 lands: confirm the service deploys from the **`stable`**
  branch, not `main`.

## 4. Onboard the customer (with them, ~15 min)

1. Send them the URL and their password; they sign in once per device.
2. Settings → **Business** → set their business name and upload their logo
   — this brands the app header, the login screen, the installed app's
   name and the calendar feed. Do this BEFORE they install to the home
   screen so the install picks up their name.
3. **Install to home screen** — Safari share → Add to Home Screen
   (iPhone) or Chrome ⋮ → Add to Home screen (Android).
4. Settings → **Connect Xero** → sign into *their* Xero.
5. Settings → Materials (Xero Items) → **Refresh from Xero**, then pick
   their default products per role.
6. Settings → set **day rate, markup, deposit** and skim the coverage/time
   rates with them.
7. Optional: Settings → Scheduling → **Calendar feed** on their phone
   calendar.
8. Point them at the user manual: `docs/user-manual/` (or send the PDF).

## 5. Offboarding a customer

1. Have them (or you) run Settings → **Export everything** and send them
   the JSON — their data is theirs.
2. On request, also give them a full database dump
   (`pg_dump $DATABASE_URL`).
3. In Xero (their side): Settings → Disconnect Xero, or they revoke the
   app connection from their Xero account.
4. Remove the instance's redirect URI from the Xero developer app.
5. Delete the web service and database on Render. That destroys their
   hosted data — which is the point, and why step 1 comes first.

## Troubleshooting

- **First deploy fails at provision:** check `DATABASE_URL` wiring — the
  database may still have been creating when the deploy started. Retry the
  deploy; provision is idempotent.
- **Customer locked out (password lost):** set a new `APP_PASSWORD` env
  var on their service and redeploy — sessions survive, the new password
  takes effect for new logins.
- **"Too many attempts":** the login throttle locks an IP for 15 minutes
  after 8 failures; a service restart also clears it.
- **Xero connect loops or fails:** the instance's exact callback URL must
  be in the Xero app's redirect list, and `XERO_REDIRECT_URI` must match
  it character-for-character.
